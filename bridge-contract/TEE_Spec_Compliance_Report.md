# Bridge-Contract vs. TEE Rollup Specification

## Executive Summary

- The current Compact contracts cover basic deposit, withdrawal proofing, and batch bookkeeping, but they do **not** satisfy key requirements of the "TEE Rollup Technical Specification (Draft)" for Midnight L2. The most critical gaps are in the TEE attestation flow, Security Council policy anchors, data availability commitments, and anti-censorship/forced-inclusion guarantees.
- Several implementation choices (monolithic contract, SHA-256 based hashing, 16-level withdrawal tree, hard-coded 3-signer verifier set) diverge materially from the specification and would prevent the contracts from interoperating with the described off-chain components.
- Some specification items are partially addressed (e.g., `BatchPublicData` fields exist, L1 message queue stores rolling hashes and timestamps), but they often lack the validation or domain separation the spec mandates.

## Additional Observations

1. **Partial alignment with L1 storage layout:** The contract keeps `committedBatches`, `finalizedStateRoots`, `withdrawRoots`, and queue indices as described in §4.1–§5.1, and tracks rolling hashes plus timestamps [bridge-contract/src/L1Rollup.compact#L70-L115](bridge-contract/src/L1Rollup.compact#L70-L115). These portions match the storage tables in the spec.
2. **Missing governance/address types:** Spec requires `mapping(address => bool)` for sequencers/finalizers and exposes council membership for auditing (§4.3, §4.4). The implementation stores `Set<Bytes<32>>` of raw public keys and never emits events or maintains historical epochs, so external observers cannot audit membership changes.
3. **No policy anchors for TEE images:** There is no on-chain record equivalent to `approvedMeasurements` or `minTcbVersion`. Thus, governance cannot publish which VM image the council should accept, contrary to §4.4.
4. **L2 modules are simulation-only:** `Bridge.compact` explicitly initializes `L2Gateway`, `L2Messenger`, and `L2MessageQueue` "for local simulation" [bridge-contract/src/Bridge.compact#L1-L40](bridge-contract/src/Bridge.compact#L1-L40). This diverges from the spec, which treats those modules as actual L2 components implemented in the L2 client/TEE, not embedded in the L1 contract.
5. **Withdrawal proof verification depth mismatch:** `WithdrawProof16` fixes tree depth at 16 siblings [bridge-contract/src/L1Rollup.compact#L45-L53](bridge-contract/src/L1Rollup.compact#L45-L53), conflicting with the spec’s 40-level tree. Even if the L2 queue were enlarged, on-chain proofs could never cover more than 2^16 leaves.
6. **No explicit DA commitment hashing rules:** The implementation never exposes helper circuits for Poseidon2-based DA commitment or batch hash computation (§10.2). Instead, `batchHash` is assumed to be provided externally without on-chain recomputation or verification beyond equality with the committed value.
7. **TIMESTAMP policy mismatch:** Spec bases queue enforcement on stored timestamps to support enforced-mode timeouts (§5.1, §11.3). Although timestamps are stored [bridge-contract/src/L1Rollup.compact#L96-L112](bridge-contract/src/L1Rollup.compact#L96-L112), no logic consumes them, so mode-switching conditions cannot be implemented.

## Recommendations

1. **Refactor per-layer contracts:** Split Gateway, Messenger, MessageQueue, and RollupChain into dedicated Compact modules with immutable references to match §2.2. Until then, upgrade risk and auditing complexity remain unacceptable per the spec.
2. **Adopt the spec’d cryptography:** Replace every `persistentHash` call used for consensus-critical data with Poseidon2 over canonical ABI encoding, and add the `councilDigest` domain separator that incorporates `rollupChain`, `layer2ChainId`, `rollupId`, `batchIndex`, and `councilEpoch` (§6.2.1–§6.2.2).
3. **Add council policy anchors and epochs:** Introduce storage for `approvedMeasurements`, `minTcbVersion`, council membership arrays, and `councilEpoch`, along with events for governance updates (§4.4). Wire these values into the attestation verification flow even if enforcement is off-chain.
4. **Validate DA parameters on-chain:** Extend `finalizeBatch` to check monotonic ranges for `daStartHeight`/`daEndHeight`, recompute `daCommitment` (or at least store it for auditing), and ensure it matches the committed batch hash (§10.2).
5. **Scale withdrawal tree:** Rework `L2MessageQueue`/`WithdrawProof` to 40 levels (or a dynamically growing tree) so withdrawals remain possible long-term (§9.4), and drop the `assert(index < 65536)` guard.
6. **Implement enforced-mode progress:** Add timers around queue timestamps and a public `commitAndFinalizeBatch` path as described in §11.3 to maintain liveness during sequencer faults.
7. **Document simulation helpers vs. production code:** If the bundled L2 modules are strictly for local testing, isolate them from the production contract package or guard them behind feature flags to avoid confusion during audits.

## Conclusion

While the bridge-contract package captures several bookkeeping aspects of the Midnight bridge, it omits or redefines the most critical trust assumptions codified in the TEE Rollup specification. Without substantial rework—particularly around TEE attestation binding, council governance, data availability proofs, and withdrawal scalability—the implementation cannot be considered compliant with the published architecture.
